# Research: Напоминания о возврате книг

Нерешённых `NEEDS CLARIFICATION` нет: единственный вопрос закрыт в сессии clarify (окно всегда
3 дня). Ниже — технические решения, которые спека оставила плану.

## 1. Представление срока и «взята ли книга»

- **Decision**: поле `dueDate?: string` в `Book`, формат `YYYY-MM-DD`. Есть поле — книга взята;
  при возврате свойство удаляется (`delete`), а не ставится в `null`.
- **Rationale**: строка в формате ISO-даты сравнивается лексикографически и не несёт времени и
  часового пояса (спека: «календарная дата»). Отсутствующее поле оставляет тела существующих
  ответов (`POST /books`, `GET /books`, экспорт) байт-в-байт прежними (FR-012, конституция IV).
- **Alternatives considered**: `dueDate: string | null` (отклонено: добавляет ключ во все
  существующие ответы); `Date` / timestamp (отклонено: тянет время и пояс, которых нет в
  требованиях); отдельный флаг `borrowed` (отклонено: второе состояние, которое может
  разойтись с датой).

## 2. Разбор и проверка даты

- **Decision**: `parseDueDate(value: unknown): string` в `storage.ts`. Принимает только строку,
  точно соответствующую `^\d{4}-\d{2}-\d{2}$`, и проверяет, что такая дата существует
  (через `Date.UTC` и сверку года, месяца, дня после разбора). Иное — `InvalidDueDateError`.
  Дата в прошлом допустима (спека, Edge Cases).
- **Rationale**: «31 февраля» должно отклоняться (спека), а `new Date("2026-02-31")` молча
  переносит дату на март; строгая сверка исключает такой сдвиг. Тот же приём, что у
  `parseExportFormat` в `001`.
- **Alternatives considered**: `Date.parse` без сверки (отклонено: принимает невозможные даты и
  нестрогие форматы); сторонняя библиотека дат (отклонено: конституция III).

## 3. Окно «скоро» и границы

- **Decision**: пусть `left` — число календарных дней от сегодня до срока. `left < 0` →
  `overdue`; `0 <= left <= 3` → `due-soon`; `left > 3` или срока нет → в список не попадает.
  Срок «сегодня» (`left = 0`) — `due-soon`, не `overdue` (спека, Edge Cases).
- **Rationale**: «окно 3 дня, включая день срока» понято как «срок наступает сегодня или в
  ближайшие 3 дня». Если нужно трактовать как 0–2 дня, меняется одна константа и два теста
  границы; решение вынесено в именованную константу `REMINDER_WINDOW_DAYS = 3`.
- **Alternatives considered**: окно 0–2 (отклонено: читается как «в течение трёх дней»
  включая сегодня, но менее естественно для «за три дня до срока»); настраиваемое окно
  (отклонено в clarify).

## 4. Источник «сегодня»

- **Decision**: `getReminders(today: string = localDateString()): Reminder[]`. Параметр —
  строка `YYYY-MM-DD`; значение по умолчанию собирается из локальных `getFullYear` /
  `getMonth` / `getDate`. Разница дней считается через `Date.UTC` по компонентам дат, чтобы
  переход на летнее время не давал сдвиг в сутки.
- **Rationale**: спека требует локальную дату машины; `toISOString()` даёт UTC и в вечерние
  часы показал бы вчера или завтра. Параметр делает расчёт детерминированным в тестах без
  подмены часов.
- **Alternatives considered**: `vi.useFakeTimers` во всех тестах (отклонено: хрупче и скрывает
  зависимость от часов); хранить «сегодня» глобально в модуле (отклонено: неявное состояние).

## 5. Форма API и коды ошибок

- **Decision**: `PUT /books/:id/due` с телом `{ dueDate }` (идемпотентная замена);
  `POST /books/:id/return` по образцу `POST /books/:id/read`; `GET /books/reminders`. Неверная
  дата → `400 { detail }` (так решено в `001` для некорректного входа); несуществующая книга →
  `404 { detail: "Book not found" }`. Номер книги разбирается как в соседних ручках
  (`Number(req.params.id)`).
- **Rationale**: следует существующим соглашениям и конституции IV. Замечание: проверка названия
  в `POST /books` отвечает `422` — это существующий контракт, он не меняется заодно с другой
  задачей.
- **Alternatives considered**: `PATCH /books/:id` (отклонено: общий патч расширяет контракт на
  поля, которых требования не называют); `DELETE /books/:id/due` для возврата (отклонено:
  «вернуть книгу» — действие домена, а не удаление ресурса, и симметрично `/read`).

## 6. Порядок и форма напоминаний

- **Decision**: элемент — `{ id, title, dueDate, status }`; сортировка по `dueDate` по
  возрастанию, при равных датах — по `id`. Просроченные автоматически идут первыми.
- **Rationale**: прямо следует FR-007 и FR-008; тай-брейк по `id` делает порядок
  детерминированным.
- **Alternatives considered**: отдавать два списка (`overdue`, `dueSoon`) (отклонено: спека
  требует единый упорядоченный список).
